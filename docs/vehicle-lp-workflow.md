# 車種別買取LP 制作・公開運用ガイド

Bimport の車種別買取LP（`https://bimport.jp/<slug>/`）を、**少ない依頼から下書き完成・公開まで進めるための運用ルール**です。
DEFENDER（`/defender/`）と PORSCHE 911（`/porsche-911/`）の制作で確定したルール・確認項目・公開手順をまとめています。

| ドキュメント | 役割 |
|---|---|
| **docs/vehicle-lp-workflow.md**（この文書） | 実際の制作・確認・公開の運用（何を、どの順で、どこまで自動で進めるか） |
| [docs/vehicle-lp.md](vehicle-lp.md) | 技術仕様（ファイル構成・車種データの項目・テンプレートの動き） |
| [docs/vehicle-template.json](vehicle-template.json) | 車種データのひな形（ビルド対象外） |

---

## 0. 基本方針

- ユーザーからの依頼は「車種名＋写真＋実在する買取実績（あれば）」程度を想定する。
- 不足しているコピー・SEO・査定ポイント・FAQ・デザインは、**この文書のルールに従って自分で作る**。確認質問は最小限にする。
- ただし **事実情報（実績の数字・装備・世代やグレードの構成など）は推測で作らない**（→「3. 絶対に捏造しない情報」）。
- 最初は必ず `"draft": true` で作り、ユーザーの公開承認を受けてから `draft: false` にする。
- 既存ページ（トップ・プライバシー・公開中の車種LP）に意図しない変更を入れない。
- ブランド表記は常に「**Bimport**」（B だけ大文字）。

### 確認質問をしてよい場面（それ以外は自分で判断して進める）

| 状況 | 対応 |
|---|---|
| 写真が1枚もない／車種と違う写真しかない | 不足を報告（文字だけのFVで下書きは作れることも伝える） |
| 実績の価格・年式・走行距離・買取時期・地域のどれかが分からない、または矛盾している | 該当箇所だけ質問（買取実績カードはこの5項目の表示枠が固定で、空欄だと空の枠が出るため）。分かっている部分で作業は進めておく |
| 車種名が複数の車を指しうる（例：世代違い・別モデルと同名） | どの車種かだけ質問 |
| 世代・グレード構成が確認できる資料で裏付けられない | 粗い選択肢（「限定車・特別仕様車」「その他・わからない」で受ける）にして進め、確認報告で「要確認」として伝える |
| コピー・SEO・FAQ・査定ポイント・配色 | **質問しない**。ルールに従って作り、スクリーンショットで確認してもらう |

## 1. ユーザーから受け取る情報

### 最低限
- メーカー
- 車種
- 写真（FV用。できれば LINE写真査定用の別カットも）
- 実在する買取実績（ある場合のみ）：価格、年式、走行距離、グレード、買取時期、地域、装備、他社との差額 など分かるもの

### あれば使う（なければ自分で作る）
- 狙いたい検索キーワード
- 特別に入れたいコピー
- 特別に入れたいFAQ
- 車種のイメージカラーの希望

依頼の例：

> Audi A7の買取LPを作って。写真はこれ。実績は○○万円、○年式、○km。

## 2. 標準フロー

```
PHASE 1 素材確認 → PHASE 2 車種調査・データ作成 → PHASE 3 draftでLP作成 → PHASE 4 車種専用デザイン
 → draft時の自動チェック → ユーザー確認（スクリーンショット） → 公開承認 → 公開手順（PR・マージ・デプロイ確認）
```

作業ブランチは、そのセッションで指定されたブランチを使う。前回のPRがマージ済みなら、最新の `main` から作り直してから作業する。

### PHASE 1：素材確認

1. 写真を確認する：枚数、解像度、どの車種・色か、FV向き（横長・車両全体）か、別カットがあるか。
2. 実績を確認する：数字と項目を書き出す。欠けている項目は**推測で埋めない**。
   - 価格・年式・走行距離・買取時期・地域は買取実績カードに必ず表示枠がある。欠けていればユーザーに確認する。
   - グレード・装備（`details`）・他社との差額（`compare`）は、分からなければ書かない（表示されないだけで崩れない）。
3. 実績の写真が「実際に買い取った車両」かどうかを確認する。分からなければFVや実績に使わない。

### PHASE 2：車種調査・データ作成

`src/_data/vehicles/<slug>.json` に入れる内容を決める。

| 項目 | ルール |
|---|---|
| `slug` | `メーカー-車種` の半角小文字・ハイフン（例：`audi-a7`、`porsche-911`、`mercedes-benz-g-class`）。既存の `/defender/` のように車種名だけの slug は、その車種名だけで一意に通じる場合に限る |
| `maker` / `model` | 英字の正式表記（例：`AUDI` / `A7`）。FV・フォーム・通知メールに出る |
| `makerJa` / `nameJa` | 日本語表記（例：`アウディ` / `アウディA7`）。`nameJa` は「今の○○、いくらになる？」などで自然に読める形 |
| `seo.title` | 原則 `{makerJa}{車種名}の買取・高価査定ならBimport｜輸入車専門`（例：「ポルシェ911の買取・高価査定ならBimport｜輸入車専門」） |
| `seo.description` | 110〜130文字。車種名、代表的な世代・型式、査定で見るポイント（グレード・装備など）、「売却未定でも60秒の入力で概算査定額をご案内」「査定無料・全国対応」を自然に入れる |
| `hero.label` | `{車種名} 買取・査定` |
| `hero.catch` | 原則「その{model}、本当の価値まで<br>評価されていますか？」。車種に合う別案があれば可 |
| `hero.lead` | 原則「売却未定でもOK。<br>まずは概算価格だけでもお気軽に。」 |
| `hero.cta` | 「60秒で概算査定」 |
| 分類（`form.bodyTypeLabel` / `form.bodyTypes`） | 車種に合う分類を1つ選ぶ：**世代**（911の992/991…）、**型式**、**ボディタイプ**（DEFENDERの90/110/130）など。最後に「わからない」を入れる。分類が不要なら `bodyTypes` を書かない |
| グレード | 分類ごとに主要グレードを並べ、最後に「限定車・特別仕様車」を入れる。「その他・わからない」は `form.gradeFallback` で自動的に最後に付く |
| 年式（`yearFrom` / `yearOlderLabel`） | 対象とする最も古い世代に合わせる |
| 査定ポイント（`points`） | 6項目（上段3つは明るいタイル＋英字ラベル、下段3つは `tone: "dark"`）＋「そのほかにも確認」の `more` ＋締めの `close` |
| 車種固有FAQ（`faq`） | 3〜4問。古い年式・MT/限定車・純正オプション・社外パーツ など、その車種で聞かれやすいこと |
| LINE写真査定（`line`） | 「あなたの<span class="lp-en">{model}</span>、<br>まずは写真で概算査定。」＋共通の lead、ボタン「LINEで写真査定する」 |
| 最終CTA（`final`） | label `{maker} {model}`、title「今の<span class="lp-en">{model}</span>、<br>いくらになる？」 |

#### 世代・グレードの調べ方
- メーカー公式の資料（車種の歴代ラインアップ、カタログ、プレスリリース）など、**確認できる情報だけ**で組み立てる。
- 細かな限定車・特別仕様車をすべて並べる必要はない。「限定車・特別仕様車」「その他・わからない」で受けられれば十分。
- 世代によって存在しないグレードを並べない（例：996 に Carrera S は入れない）。
- 自信のない世代は、選択肢を少なくして「限定車・特別仕様車」「その他・わからない」で受ける。確認報告で「要確認」として伝える。
- 選択肢の表記は英字グレード名を基本にし、補足は全角括弧で付ける（例：「GT3（ツーリング含む）」）。

#### コピー・FAQの書き方
- 金額・順位・件数・「必ず」「最高額」などの断定はしない。
- FAQの回答は「ご相談いただけます」「確認したうえでご案内します」のように、実際の対応範囲を超えない表現にする。
- 査定ポイントの説明は短く（1行〜2行）、事実として確かなこと（その装備・仕様を確認する、という内容）に留める。

### PHASE 3：draftでLP作成

1. `src/_data/vehicles/<slug>.json` を `"draft": true` で作る（[docs/vehicle-template.json](vehicle-template.json) をコピー）。
2. 画像を `src/assets/images/<slug>/` に置く（→「4. 写真のルール」）。
3. **車種ごとの Nunjucks ページはコピーして作らない**。ページは共通テンプレートから自動生成される。
4. 共通テンプレートで表現できないことがある場合だけ、テンプレートに**任意項目**を追加する。追加した項目を指定しない既存の車種の出力が変わらないことを必ず確認し、[docs/vehicle-lp.md](vehicle-lp.md) に追記する。

### PHASE 4：車種専用デザイン（テーマCSS）

- 基本構造とCV導線は共通のまま、**配色と装飾だけ**をテーマCSSで変える。
  - 例：DEFENDER＝黒・白・ゴールド（共通デザインのまま。テーマなし）
  - 例：PORSCHE 911＝黒・白・深い赤＋少量のゴールド（`themes/porsche.css`）
- 作り方：`src/assets/css/themes/<theme>.css` を作り、車種データに `"theme": "<theme>"` を書く。すべてのセレクタを `.lp-theme-<theme>` で始める。
- 主に変えるもの：アクセント色のトークン（`--c-gold`・`--c-gold-text`・`--c-gold-grad` など）、ボタンの文字色、FVの英字の大きさ、写真の表示位置。
- 共通のまま変えないもの：フォームの構造、Bimportが選ばれる理由、口コミ、GAS送信、LINE導線、CVの配置と順番。
- メーカー公式サイトのデザイン・ロゴ・書体・コピーを模倣しない。メーカーのロゴは使わない。
- 文字と背景のコントラストを保つ（赤や明るいアクセント色の上の文字は白にするなど）。

## 3. 絶対に捏造しない情報

以下は、**ユーザー提供の情報、または確認できる実データだけ**を使う。分からなければ書かない・表示しない。

- 買取価格、年式、走行距離、買取時期、地域、他社との差額（「2位の会社より○万円高く」）
- Google評価点、Google口コミ件数
- 年間実績などの数字
- 実績車両の装備・オプション、限定車であること
- その他、実績にもとづく数字すべて

ルール：
- 実在する買取実績がない車種は `cases` を空にする（買取実績セクションは自動で非表示）。
- 架空の実績・サンプル実績を本番ページに載せない。
- 口コミは共通の3件（`src/_data/reviews.json`）を使い、担当者の個人名は表示しない。
- Google評価点・口コミ件数は、確認済みの実データがない限り表示しない。

## 4. 写真のルール

### 最適化
受け取った写真をそのまま使わず、Web用に最適化する（このリポジトリの作業環境では ImageMagick の `convert` が使える）。

```bash
D=src/assets/images/<slug>
convert 元画像 -strip -background white -flatten -quality 82 -interlace Plane -sampling-factor 4:2:0 $D/hero-1672.jpg   # JPEGフォールバック
convert 元画像 -strip -resize 1000x -quality 80 -define webp:method=6 $D/hero-1000.webp                              # スマホ用WebP
convert 元画像 -strip -resize 1672x -quality 82 -define webp:method=6 $D/hero-1672.webp                              # PC用WebP
```

- 目安：横幅 1672px（PC）と 1000px（スマホ）、JPEG は 200KB 前後以下。
- 元画像が 1672px より小さい場合は拡大しない（元の幅のまま）。
- ファイル名は用途＋幅：`hero-1672.jpg`、`hero-1000.webp`、`line-photo-1672.jpg` など。
- 車種データの `images.hero.webp` / `images.line.webp` に WebP を登録すると `<picture>` で配信される。

### 写真の割り当て（推奨）

| 場所 | 使う写真 |
|---|---|
| FV（`images.hero`） | メインビジュアル（車両全体が写った横長のカット） |
| 買取実績（`cases[].image`） | 実際に買い取った車両の写真のみ |
| LINE写真査定（`images.line`） | FVとは別のカット |
| 最終CTA（`images.final`） | FV画像または別画像 |

- 同じ写真をページ内で何度も使いすぎない。
- 素材が足りない場合、**無関係な画像（別の車種・別の個体）を使わない**。未指定にしてテンプレートのフォールバックに任せるか、不足を報告する。
  - LINE写真査定・最終CTAは、未指定ならFV画像、それもなければ黒背景になる。
  - 実績の写真がなければ、車のアイコンのタイルになる。

### トリミング
- FVは PC 1440px・スマホ 375px・320px で、車両のフロント・ルーフ・ホイールが不自然に切れないように調整する。
- 調整は車種データの `images.hero.position` / `positionPc`、`images.line.position` / `positionPc`（`object-position`）で行う。足りなければテーマCSSで写真枠の比率を調整する（911の LINE写真査定の例）。

## 5. フォームとGAS

### フォーム（全車種共通）
- 3STEP概算査定フォーム（STEP1 車両情報 → STEP2 お客様情報 → STEP3 確認）を共通で使う。
- メーカー・車種は車種データから自動で入る。
- 最初の分類項目の名前は `form.bodyTypeLabel`（例：ボディタイプ／世代／型式）で決める。
  この名前は、フォームの見出し・確認画面・通知メールで共通に使われる（送信データの `bodyTypeLabel`）。
- 分類を選ぶとグレードの選択肢が切り替わる。

### GAS（Google Apps Script）
- 送信先は `src/_data/site.json` の `estimateEndpoint`（公開して問題のないURL）を全車種で共通に使う。
- **GAS v2 が本番に反映済み**。`bodyTypeLabel`（20文字まで、なければ「ボディタイプ」）を受け取り、通知メールに「世代：992」「ボディタイプ：90」のように出す。
- 新しい車種を追加するだけなら **GASは変更しない**。
- 通知先メールアドレスなどの秘密情報は、GASのスクリプトプロパティだけで管理する。GitHub・公開HTML・車種データには絶対に書かない。
- GASのコードはこのリポジトリに置かない（ユーザーのApps Scriptで管理）。

### フォームを変更した場合に確認すること
- 送信成功（完了画面）／送信失敗（エラー表示・再送できる）
- 二重送信の防止（送信中はボタンが無効）
- ハニーポット（`website` 欄）
- 送信時間チェック（`elapsedMs`）
- 確認はブラウザの送信処理を止めて行い、**draft中に本番GASへ送信しない**。GAS側の挙動は、GASのコードをローカルで模擬実行して確認する。

## 6. 共通セクション

原則として、以下は全車種で共通のものを使う（車種データの文言だけ変える）。

ヘッダー／スマホメニュー／3STEP概算査定／Bimportが選ばれる理由／Google口コミ3件／買取の流れ／FAQの基本構造（共通5問＋車種固有）／LINE導線／最終CTA／フッター／スマホ固定CTA

- LINEのURLは `site.lineUrl`、Google口コミのURLは `site.googleReviewsUrl` を使い、直接書かない。

## 7. SEO

- 車種ごとに `seo.title`・`seo.description` を設定する。
- canonical と og:url は `site.siteUrl + "/" + slug + "/"`（例：`https://bimport.jp/audi-a7/`）で自動設定される。正式URLと必ず一致させる（slug を後から変えない）。
- og:image は `images.og`、なければFV画像。
- `draft: true` の間：ページに `noindex, nofollow` が付き、確認用ビルドでも本番の sitemap.xml にも載らない。
- `draft: false` にすると：noindex が外れ、sitemap.xml に自動で追加される。
- robots.txt は共通のまま（変更しない）。

## 8. draft時の自動チェック

`npm run build:preview` でビルドし、PC 1440px・スマホ 375px・スマホ 320px で確認する（Playwright でブラウザ表示・スクリーンショット）。

| 確認項目 | 内容 |
|---|---|
| 横スクロールなし | ページ幅が画面幅を超えない |
| 画像切れなし | すべての画像が読み込まれ、車両が不自然に切れていない |
| 文字切れなし | 見出し・ボタン・選択肢の文字がはみ出さない |
| JSエラーなし | ページ表示・フォーム操作中にエラーが出ない |
| フォーム3STEP | STEP1→2→3と進める。未入力時のエラー表示 |
| 連動 | 分類（世代など）ごとにグレードが切り替わる。「わからない」で「その他・わからない」が自動選択 |
| 確認画面・完了画面 | 項目名（`bodyTypeLabel`）と値が正しく出る。完了画面が出る（送信は止めて確認） |
| 送信データ | maker・model・bodyType・bodyTypeLabel・grade などが正しい |
| LINEリンク | すべて `site.lineUrl` |
| Google口コミリンク | `site.googleReviewsUrl` |
| canonical・og:url | `https://bimport.jp/<slug>/` |
| noindex | `noindex, nofollow` が付いている |
| 本番sitemap | 通常の `npm run build` で、ページも sitemap.xml の掲載もないこと |
| 既存LPへの影響 | 下の「既存ページの保護」 |

### 既存ページの保護
- 作業前の `npm run build` の出力を保存しておき、作業後の出力と比べる。トップ・プライバシー・公開中の車種LP・robots.txt が**1バイトも変わっていない**ことを確認する。sitemap.xml は draft 中なら変化なし。
- 共通テンプレート・共通CSS・共通JSを変更した場合は、既存の車種LPを 1440/375/320px で作業前と比べ、表示差分が0であることも確認する。差分が出たら原因を直してから進む。

## 9. ユーザー確認（draft完成後）

技術的な詳細は毎回並べない。代表的なスクリーンショットを送り、短く確認する。

送るスクリーンショット（主にスマホ375px、必要に応じてPC）：
- ファーストビュー
- フォーム
- 買取実績（ある場合）
- LINE写真査定
- 査定ポイント
- 最終CTA

確認のまとめ方（例）：

> Audi A7 の買取LP（下書き）ができました。スクリーンショットをご確認ください。
> デザインと内容がこれで良ければ公開へ進みます。

あわせて伝えるのは次のものだけ：
- 事実情報で要確認の点（例：世代・グレード構成で裏付けが弱い部分、実績の欠けている項目）
- 素材の不足（例：LINE写真査定用の別カットがない）
- 技術的な問題があった場合の詳細

## 10. 公開手順（「OK」「公開して」「これで進めて」などの承認後）

承認を受けたら、以下を可能な範囲で連続して行う。ユーザーが「PRまで」「マージはしないで」などと指示した場合は、その指示を優先する。

1. 車種データを `"draft": false` にする
2. `npm run build`
3. noindex が外れたことを確認
4. sitemap.xml に `https://bimport.jp/<slug>/` が自動追加されたことを確認
5. 既存ページへの影響がないことを確認（「既存ページの保護」）
6. commit（変更内容が分かる日本語のメッセージ）
7. push（指定の作業ブランチ）
8. `main` 向けの Pull Request を作成（概要・変更内容・確認したことを書く）
9. `main` との差分を確認（意図しないファイルが入っていない）
10. `main` へマージ
11. GitHub Actions「Deploy B import LP」の完了（build・deploy とも成功）を確認
12. 公開URL `https://bimport.jp/<slug>/` を確認
13. `https://bimport.jp/sitemap.xml` を確認
14. `https://bimport.jp/robots.txt` を確認
15. 公開ページの canonical・og:url が正式URLで、noindex がないことを確認

補足：
- クラウドの作業環境は、ネットワーク設定によって `bimport.jp` に接続できないことがある。その場合は、`main` のビルド結果が公開前に確認したビルドと一致することで代わりに確認し、公開URLの目視確認をユーザーに依頼する（環境の Network access に `bimport.jp` を追加すれば直接確認できる）。
- 作業ブランチの削除がこの環境からできない場合は、PRのページから削除するよう案内する。

### 本番フォームの確認（初回公開時に1件だけ）
- 可能であれば、テストと分かる内容で**1件だけ**送信する。**二重送信・再送はしない**（失敗しても自動で再送しない）。
- 公開ページを操作できない環境では、フォームと同じ形式のデータをGASへ1件だけ直接送ってよい。
  - 例：お名前「テスト送信（{車種名}公開確認）」、電話番号 090-0000-0000、分類・グレードは代表的なもの、年式・走行距離は「わからない」、`tracking: { utm_source: "production_test" }`、ページ `https://bimport.jp/<slug>/`
- GASの応答（`{"ok":true}`）を報告し、ユーザーには**通知メールが届いたかだけ**確認してもらう。

### Search Console
- 公開した車種は sitemap.xml に自動で追加されるため、サイトマップを毎回再送信する必要はない。
- 重要な車種や早くインデックスさせたいページだけ、公開後に URL検査 →「インデックス登録をリクエスト」を行う。
- Search Console の操作はユーザーにしかできないため、必要な場合は**最後に1つの作業として案内する**。

## 11. 既存ページの保護（まとめ）

- 新しい車種LPの作成で、トップページ・プライバシーポリシー・公開中の車種LP（DEFENDER・PORSCHE 911 など）に意図しない変更を入れない。
- 既存の車種データ・画像・テーマCSSは、その車種の修正依頼がない限り変更しない。
- 共通テンプレートを変更した場合は、既存LPの表示差分を確認する（「8. draft時の自動チェック」）。
- `site.json` の共通設定（LINE URL・GAS送信先など）は、依頼がない限り変更しない。
